## 4. 已踩的坑（别重复踩）

### 真机 / adb

- **输入法会挡 tap**：坐标对、按钮 enabled、logcat 干净，就是点不动。
  uiautomator 只 dump 应用窗口看不到 IME。**方案：点空白处收键盘**
  （已实装在 `EditScreen` 根节点的 tap 手势，`clearFocus()` + `keyboard?.hide()` 两个都调）。
  `adb shell ime disable` **没用**——MIUI 会自动补位，实测绕不过去，别再试。
- **客观验键盘**：`adb shell dumpsys input_method | grep mInputShown`。别看截图判断。
- **截图会滞后显示旧帧**，与 dump 打架时**信 dump**。
- **布局会漂**：输入框填内容后行高变化，按钮 y 坐标下移。每次点击前重新 dump。
- **`input text` 进不去中文**。真机验证用 ASCII 顶上，中文语义交给 JVM 测试。
- **`adb shell input motionevent` 测不出「返回提交」**：单步 MOVE 没 fling 速度，
  系统不认。要用 `input swipe`（自带速度）测提交分支。motionevent 只适合测
  「中途预览」和「滑回撤销」。
- **`BackEventCompat` 的边缘常量是 `EDGE_LEFT`/`EDGE_RIGHT`**，不是 SWIPE_EDGE_*。
- Git Bash / MSYS：`MSYS_NO_PATHCONV=1` 用于设备侧路径；`adb pull` 的**本地目标**
  要写 Windows 路径。

### Compose 手势 / 命中测试（2026-10-03，标签删除时连踩两个）

- **`Modifier.offset` 的命中测试跟着 placement 走——必须写在最外层**：
  "滑开露出按钮"的容器里，行内容的 `offset` 如果写在 `anchoredDraggable`
  **里面**，拖动层的命中区仍停在未平移的整行范围，把底下露出的按钮全盖住
  ——真机表现是"按钮明明露着，点它毫无反应"。把 `offset` 提到拖动层之前即修复。
- **"谁滑开着"的同步不能靠反向推断（竞态）**：起初写成"我开着但父级没认领 = 关自己"，
  真机上表现为"一露头就弹回去"——落定那一刻父级状态还没更新，被误判成
  "别行开了"。正确判据：**只有父级明确指定了别的行**（openRowId 非空且非我）才关自己。

### Compose 动画 / 尺寸（2026-10-03，编辑页展开动画连踩四个）

- **`AnimatedVisibility` / `AnimatedContent` 的内容按「一个布局单元」对待**：
  直接摆一串并列子节点（分隔线、输入框、按钮）**不会纵向排列，而是全部叠在同一
  原点**。真机表现：展开后一坨东西压在一起，dump 里几个节点 y 完全相同。
  规矩：**内容必须包一层 Column/Box，一个分支一个根节点**。
- **动画必须跑在带帧时钟的作用域里**：`animate()` 靠 `withFrameNanos` 推进，
  而 Activity 的 `lifecycleScope` 上下文里**没有 `MonotonicFrameClock`**，
  一调就抛异常当场闪退（真机：编辑页取消、密钥/导出页返回全崩）。用组合体里的
  `rememberCoroutineScope()`。**线索**：手势返回一直没事、按钮返回必崩——
  因为 `PredictiveBackHandler` 的挂起上下文自带帧时钟。
- **`animateContentSize` 只动「外层报告的尺寸」**，内容本身第一帧就按最终大小排好：
  看着是"框瞬间跳到位、外面的空白慢慢合上"，**边框并不会拉伸**。要边框真拉伸，
  只能在动画期间**按插值高度重新测量**
  （`Modifier.layout` 里 `measure(constraints.copy(minHeight = h, maxHeight = h))`）。
- **尺寸动画必须是一个连续函数，不能"动画中压高度、静止时放开"**：那种两套模式的
  写法在交班那一帧要切换测量方式，两端对不齐就是一次可见闪跳（真机反馈
  "拉伸到位之后消失再出现"）。正解：两端**恰好等于两个形态的自然高度**，全程无开关；
  真值只需量一个（Material 框高 = 行数×行高 + 固定留白，另一半用行高推算）。
- **200ms 的动画截图抓不住，用日志验**：临时在 `layout` 里打 `p / 目标高度 / 实测高度`，
  `adb shell input tap` 自己驱动 UI，`adb logcat -d -s <tag>:D` 读逐帧数值——
  单调、两端落点正确就是对的。验完把日志删掉（当时的实现见当日工作记录）。

### Compose 换位动画 / keyed group（2026-10-03 视觉复查抓出的真 bug）

- **现象**：标签管理**值层**上下移动是瞬移、滑开状态不跟行；同屏**维度层**一切正常。
  两层共用同一个 `swapShift`，差别只在"行是怎么渲染的"。
- **根因（真机插桩 + 逐帧日志定位）**：`key()` 要生效，**两条缺一不可**——
  ① key 块是**列表容器的直接子节点**（不能包在 `if/else`/`when` 里）；
  ② 块内只放**一个 composable 调用**（不能直接写条件、或调用块外定义的 lambda）。
  否则运行时不当它是可迁移组：条件包裹 → 重排即整组重建；
  直接写条件/外置 lambda → 按位置复用。两种都表现为 `lastIndex` 恒等于 `index`、
  effect 不重启 → 动画永不触发。维度层恰好两条都满足，所以一直是对的。
- **修法**：值层每行抽成 `ValueRow` composable，`key(tag.id) { ValueRow(...) }`
  （`TagOrderScreen.kt`）。附加收益：滑开露删除的状态现在也随行迁移。
- **教训**：`key()` 写了 ≠ 生效。"状态跟着槽位走、参数却正常更新"这种半吊子
  失败模式**光读代码看不出来**，必须插桩（在 `swapShift` 里打 `index`/`lastIndex`，
  再打 `Animatable` 的逐帧值）。四个错误假设被实测逐个打掉后才定位到真因。
- **观测手段的实测边界**（都是这次验出来的）：
  ① **Android 14+ 的应用读不到 `animator_duration_scale`**（`ValueAnimator.getDurationScale()`
  恒 1.0）——想用系统"动画缩放"把 Compose 动画放大再抓帧，在本机**不可行**；
  ② **raw `screencap` 连拍约 200ms/帧**（写 `/data/local/tmp` 比 `/sdcard` 快近一倍），
  糊不住 220ms 的动画，只能做旁证；**逐帧日志才是可靠观测手段**；
  ③ 做连拍前先来个**对照实验**（下拉通知栏等必有动画的动作）验证"抓帧这套家伙事
  本身灵不灵"——这次正是靠它才敢断定"值层真的没动画"，而不是"没抓到"。

### 开库耗时：KDF 才是元凶（2026-10-03，实测 1 秒 → 毫秒）

- **现象**：指纹解锁后到列表出现之间有约 1 秒的"加载中…"。用户以为这是
  "解锁数据库的必要开销"——**不是**。
- **定位过程（这套手法值得复用）**：先插桩打时间戳拆段——
  Keystore 解封 2ms / 开库调用 12ms / **首查 988ms** / 首帧组合 141ms；
  再做对照「**同进程第二次解锁**」（代码全热）——**依然 1.1 秒** ⇒ 排除 JIT，
  锁定"每次开库都付的原生固定成本"，量级吻合 SQLCipher 的 25.6 万次 PBKDF2。
- **根因**：`SQLCipherDriver(key.bytes, …)` 把 32 字节全熵 DEK 当**口令**传，
  库就照规矩再跑一遍自家 KDF。当年注释写着"多余但无害"——对安全确实无害，
  但**没人量过时间**：口令模式 999~1282ms vs raw key 同口径 23~67ms。
- **修法**：DEK 以 `x'<64位hex>'` 的 raw key 形式传（SQLCipher 见此前缀跳过 KDF）；
  旧库一次性 `PRAGMA rekey` 迁移（事务内完成）。**不存迁移标记**——每次开库
  「先试 raw → 退回口令能开就当场迁移 → 都不行才报错」，天然自愈（迁移中断电、
  放回旧格式副本都能自动纠正）。实现全在接缝 A（`SqlCipherDatabaseProvider`），
  解锁路径与密钥体系一行没动。
- **真机结果**：迁移那次 940ms（一次性）；日常 指纹→列表 **163ms**（改前 1152ms）。
- **教训**：① "加密所以慢"是最容易被接受的错误归因——慢必须拆段量了再下结论；
  ② 同进程二次测量是区分"冷启动成本"与"每次固定成本"的最便宜一招；
  ③ **别把 DEK 当口令**：KDF 只为弱口令抗爆破存在，对全熵密钥不增加一个比特
  的保护，纯粹是每次解锁的固定开销。主密码那边（60 万次 PBKDF2）才是它该
  干活的地方——两处不要混。

### 锁相关

- **作废的钥匙不会从 Keystore 消失（2026-10-03 真机踩到）**：高安全模式下录入新指纹后，
  `KeyStore.getKey(alias)` **照样返回 Key 对象**——"钥匙在不在"检测不到作废。
  真正的信号是：任何 `Cipher.init` 会抛 `KeyPermanentlyInvalidatedException`
  （授权检查在 doFinal，所以 init 不需要指纹，可随时探测）。
  两个连带修正：
  ① 作废探测改成"拿它 init 一次"（`isKeyInvalidated`）；
  ② `ensureKeyExists` 不能只看"在不在"，**作废的钥匙必须先删再重造**——
  否则"重新启用指纹解锁"会继续用那把死钥匙、再次失败（真机上就是这么暴露的：
  先看到的是通用的"指纹暂时用不了"，而不是引导话术）。

- **锁周期后列表 VM 失联（2026-10-03 修，单独立过提交）**：`itemListViewModel` 是
  Activity 字段、跨锁周期存活，而 `clearSession()` 关库后 `openDatabase()` 返回**全新**
  实例——解锁后任何一次 refresh（保存/删除后回列表的必经之路）都会打在已关闭的库上，
  未捕获即崩。修法：`onStart` 里清会话的同时置空列表 VM，解锁后按新库重建。
  **这条路径此前从未被真机走过**（历史验证都从冷启动开始），是规划编辑/删除功能时审出来的；
  2026-10-03 真机回归：后台 75 秒 → 解锁 → 保存 → 列表刷新正常，logcat 本 App 零异常。

### 接缝 B 的接线坑（2026-10-01 修）

- **症状**：App 退后台超过 60 秒再回来 → **永久卡在「已锁定」**，只能杀进程。
- **根因**：`onForeground` 只负责"该不该锁"；锁上之后**没人发起重新验证**
  （`requestUnlock` 只在 onCreate 调用过一次）。
- **修法**：`onStart` 里发现回前台后处于 Locked → 发起一次验证；
  锁屏加「解锁」按钮（加密阶段"用户取消验证后重试"的路）。
  刻意**不**做成"观察 Locked 状态就发起"——用户取消验证后状态又是 Locked，
  会立刻再弹，形成弹窗循环。
- 触发条件隐蔽（要在后台待满 60 秒），所以此前设备测试没碰到。
  **以后动锁相关的代码，手动过一遍「后台待 70 秒再回来」这个场景。**
- 后续演化（3-2b-1）：锁屏从"提示 + 解锁按钮"升级为**密码锁门**（`ui/lock/UnlockGate.kt`），
  宽限期耗尽后回前台会**清会话**（关库 + 丢 DEK）而不是自动发起验证；
  自动发起留给 3-4 的生物识别（那时弹的是验证器，不是放行）。

### driver 模式下 Room 的坑（2026-10-01，切换加密库时踩到）

- **现象**：加密库切上去之后，**保存记录失败**：
  `Cannot return a SupportSQLiteOpenHelper since no SupportSQLiteOpenHelper.Factory was configured with Room.`
- **根因**：SQLCipher 用 **driver 模式**（`setDriver(SQLCipherDriver(...))`）开库，
  该模式**没有 openHelper**；而 `RoomDatabase.withTransaction` 走的是传统
  SupportSQLite 路径，要拿 openHelper → 直接抛。
- **修法**：driver 原生事务口 `data/db/Transactions.kt`
  （`useWriterConnection { it.withTransaction(IMMEDIATE) { ... } }`），
  容器接线改走它。**`@Transaction` 注解的 DAO 方法不受影响**（Room 生成的代码会适配）。
- **最值得记的一点**：**48 条仪器测试全绿也没挡住它**——那些测试都用
  `inMemoryDatabaseBuilder`（传统路径），"driver 模式 + 手写事务"这个组合从没被跑到过。
  是**真机上点一下"保存"**暴露的。已补两条仪器用例（提交成功 / 失败回滚）守这个组合。
  → 这就是"阶段收尾必须跑真机、光看测试全绿不算数"的又一个实证。

### 未解观察：被删的密钥/库文件"复活"（2026-10-01，**仅此一次，未复现**）

- **事实**：3-2b-2 真机验证收尾时，`files/recovery-key.txt` 与 `databases/noteone.db`
  被 `run-as rm` 删除，`ls` 当场确认为空 ✓；约 5 分钟后（其间跑过数次仪器测试与
  Gradle 安装）再查，两份文件**又在了**，**mtime 还是删除之前的时间**（06:47 / 06:52），
  而且信封**打不开当时的密码**。
- **已排除**：仪器测试代码不碰 `filesDir`/生产库名（grep 全库确认）；受控实验
  "删除 → `adb install -r` → 再查"**未复现**；用户 999（MIUI 分身）与主空间数据无关。
- **没来得及做**：把那封信封留着试其余历史密码（手快删掉了，证据没了）。
- **下次若再出现**：**先别删**，把文件 `cat` 出来、试几个历史密码、记下 mtime 与
  `dumpsys package` 的安装时间，再判断。若确为系统级"数据复活"，对一个

- **跑仪器测试会清空真机上的 App 数据 —— 已修复（2026-10-01）**。

  编译错误指向的却是 `.append`。要么返回 `this`，要么拆成两条语句。
- **androidTest APK 的路径**（2026-10-03 实踩）：在 `app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk`
  ——本文档旧版写的 `.../apk/debug/...` 是错的，照抄会 `No such file or directory`。
- **换签名后必须连测试包一起卸载**（2026-10-03 实踩）：`adb uninstall <包名>` 不带走

  `adb uninstall io.github.hexgmskr.noteone.test`。

  这条零输入法的路最稳。
- **进多选模式时列表整体上移**（2026-10-03 实踩）：顶部筛选条+设置行被换成更矮的

### 已知限制（有意不修，2026-10-04 审计如实记）

**主密码在内存里是 `String`，擦不掉**。`EditText → ViewModel → RecoveryKeyManager`
一路以 `String` 传递，`CharArray` 只在 PBKDF2 那一刻短暂存在。Java/Kotlin 的 `String`
不可变、无法主动清零；把全链改成可变数组也挡不住 Compose 文本层与系统 IME 的
`String` 化——收益极小而波及面大，**记录不动**。威胁模型上可接受：整库加密防的是
设备丢失/文件被拷贝（不 root、无恶意进程是本机既定前提）。

| **导出形态二选一**（2026-10-01） | 每次导出让用户选「加密」（复用副本B 的 KDF+信封，用途标识 `noteone-export`）或「明文」；**加密导出前先用主密码解一次恢复密钥核对**，错密码不备数据 | 用户拍板两样都要；核对是防"打错的密码被封进备份"——灾难恢复时才发现打不开就晚了。明文导出配确认框 |
| **导入只做合并追加**（2026-10-01，用户拍板） | 去重键 `(content, createdAt)`；不提供"清空替换" | 还没有删除记录的 UI，破坏性操作风险太大；重复导入天然幂等 |
| 导入密码框与导出密码框**分开** | 两个输入框各管各的 | 旧导出文件可能是改密码**之前**的旧密码，共用一个框会互相污染 |
| **手写 JSON 解析器**（MiniJson） | 严格语法 + 报错带行列号 + 深度上限 | org.json 在 JVM 单测里是空壳；kotlinx-serialization 不进主 classpath（债务②） |
| **标签管理并入列表页**（2026-10-03） | 「调整标签顺序」入口改名「标签管理」，功能只做**同义标签合并/重命名**；不做引用计数 | 单独开页不值得；计数无需求 |
| **正式数据走编辑入口录**（2026-10-03） | 逐条手动录入，不用导入路径 | 导入器定位是灾难恢复，不是迁移工具 |
| **记录查看/编辑优先做**（2026-10-03） | 列表卡片点击打开记录：看全文、取用（复制）、再编辑 | 数据链条缺"再使用"一环，用得起来才算闭环 |
| **启动图标**（2026-10-04） | 用户选定构图（`#` 斜挂一把锁），整图 **1:1** 映到图标可见区（不裁不放大）；模板遗留图标已清 | 生成走 `tools/make_icon.py`（换图=一条命令，自动处理边缘与自检）；用户对"放大过头"很敏感——**内容尺寸保持原图比例** |
| **暂不迁 Navigation/Hilt**（2026-10-04 评估） | 屏幕 6 个仍用手工 sealed class 返回栈 | 迁移触发条件改为**语义需求**（深链/返回栈语义）；屏幕数不再是条件。原定阈值“4–5 屏”本次评估如实推翻（CLAUDE.md 已同步） |

**中文按 Unicode 码点排序，不是拼音**（`#萌宠#灵动#自然` 实际渲染 `#灵动#自然#萌宠`）。
用户已知悉，并用自定义顺序功能消解了这个问题。

**密钥语义速查**（2026-10-03 与用户逐条对答案时澄清，理解灾难恢复的基础）：

- 拿到 DEK 的路只有两条：**创建**（`setup()` 生成随机 DEK）／**恢复**（`importFrom()`
  解封副本B）。全项目只有 `setup()` 一处生成 DEK；恢复是原样搬回，`changePassword`
  也只重包不改 DEK。
- 副本A（Keystore 包裹）不是"恢复"是"**重建**"：Keystore 钥匙不可导出、随卸载/换机销毁；
  新设备上重新启用指纹时，用会话里的 DEK 重包一份。
- **加密导出文件的链路是「主密码 → 内容」，不经过 DEK**（`Exporter` 直接 seal）。
  所以：内容恢复只认主密码；库文件副本恢复只认 DEK。走"创建新密钥"也能导入旧导出文件，
  但旧的库文件副本就永久打不开了。
- 离线灾难备份的两件套：**副本B（钥匙）+ 导出文件（内容）**。库文件副本没有 App 入口
  （仅 debug 构建 + run-as 能手工放回），不是产品功能。

- **进场用「容器变换」**（2026-10-03 用户选定，从三个方案里挑的）：新屏从**被点
  元素**的位置长成整屏（FAB、列表卡片都算），容器色插值到页面底色，起点图标由容器
  接着画、前半段淡出，内容后 65% 才淡入。拿不到合适起点（如详情 ⋮ → 编辑）退化成
  "整屏底色 + 内容淡入"，不硬凑假起点。
- **退场保持跟手侧滑，不改反向形变**（用户明确"非常丝滑"）：提交时先滑出屏幕再弹栈，
  按钮返回/保存/删除走同一套动作。
- **按钮只有两种样式（2026-10-03 三轮，用户二次修订；取代此前的"四档"表）**：
  同一区域、同一交互逻辑下的**动作按钮**收成"积极 / 非积极"两支——
  1. 积极（保存 / 完成 / 更换 / 导出 / 解锁 / 创建）= `Button`（主色实心）；
  2. 非积极（取消 / 退路 / 挑选文件 / 子流程入口）= `FilledTonalButton`
     （灰实心、**有框**。用户原话："和'关闭指纹解锁'一样的灰色，我能接受"）。
  **裸文字（`TextButton`）只留给纯导航与行内小动作**：返回 / 复制 / ⋮ / 粘贴 / 收起 /
  ↑↓ / 改名合并 / ←回到维度顺序。`OutlinedButton` 这一档不再用于动作按钮。
  底部动作栏仍是"取消在左、主操作在右"，与对话框同向；对话框内维持全 `TextButton`
  （M3 惯例）。**例外一处**：标签面板的「+ 新建」保持 chip 造型（刻意与标签同形族，
  换成实心按钮会被误认成一个标签去点）。
  配套事实：**"执行类"动作一律实心，不按"推荐程度"分轻重**——导出加密与导出明文
  同为积极按钮，"不推荐明文"由提示文字承担（见 `ExportScreen` 注释）。
  **教训**：深色底上"裸文字按钮"根本不像按钮，**按钮和谐要看真机**——
  "取消没有框"就是只有真机视角才看得出来的问题（用户原话："密钥页不也是页吗？你不看？"）。
- **标签管理页的落库语义：边改边存**（2026-10-03 用户反馈后统一）——**每次上下移动
  立刻写**顺序偏好；完成 / 侧滑返回 / 系统返回都算"留着走人"；**取消 = 恢复进来时的
  顺序**（唯一的撤销手段）。改名/合并/删除是即时生效的操作（各有确认框、有 notice
  回执），不参与取消。早先"只在点完成时落库"有两个洞：调完维度顺序侧滑返回会静默
  丢改动、重排中途改名会被 `reload()` 用库里的顺序冲掉。
  遗留杂物：`TagOrderViewModel.consumeNotice()` 目前没人调用（notice 是常驻状态行）。
- **首帧预热：评估过、决定不做**（2026-10-03）——思路是把列表页已经在内存里的快照
  （`candidateTags` / `allItems` / `ordering`）当作详情页、编辑页 VM 的初始状态，消掉
  "首帧空、几十毫秒后长出标签"的那一跳。用户真机实测**看不出来**：进场容器变换的
  内容后 65% 才淡入，等标签可见时那次查询早就回来了。**别再为它加班**；将来若某个
  页面真出现"先空一下再长出"，再给那个 VM 加一个可空种子参数（设计已想清楚，
  没写代码）。
- **「回顶部」是圆角三角楔形钮**：与新建 FAB 同色同宽、尖朝上，挨着它留一点距离，
  按钮栈展开时跟着新建卡片一起上移（相对位置不变）。**它"没有直底边"是形状的固有
  代价、用户拍板接受**——想让底边直必须同时加高三角 + 缩小圆角（代码注释里有算式）。
